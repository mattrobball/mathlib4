# Bridgeland Stability Conditions: Formalization Summary

## Overview

This document summarizes the autoformalization of Bridgeland's stability condition
theorems from the 2007 Annals paper "Stability conditions on triangulated categories."
The formalization produces sorry-free Lean 4/Mathlib definitions and theorem statements
across three files totaling 337 lines.

**Branch:** `feat/bridgeland-stability-conditions`
**Repository:** `mattrobball/mathlib4_fork`

---

## Plan

The plan called for formalizing the **statements** (not proofs) of:

- **Theorem 1.2:** The space of locally-finite stability conditions on a triangulated
  category is a complex manifold, with the central charge map a local homeomorphism.
- **Corollary 1.3:** If the category is numerically finite, the space of numerical
  stability conditions is a finite-dimensional complex manifold.

Both theorem statements are encoded as `Prop`-valued definitions that existentially
quantify over topologies, avoiding any need to construct the Bridgeland topology or
prove it is a manifold.

### Key design decisions

1. **K_0 via FreeAbelianGroup quotient** — The plan originally proposed building an
   `AddCommMonoid` on isomorphism classes via biproducts, then applying
   `Algebra.GrothendieckGroup`. During implementation, a simpler approach was taken:
   define `K_0 C` directly as `FreeAbelianGroup C` quotiented by isomorphism and
   distinguished triangle relations. This avoided universe issues and complex monoid
   constructions.

2. **Topologies existentially quantified** — Both `bridgelandTheorem_1_2` and
   `bridgelandCorollary_1_3` use `exists (tau : TopologicalSpace ...)` to avoid
   constructing the actual Bridgeland topology.

3. **`@PartialHomeomorph` with explicit topology arguments** — Since the topologies are
   existentially quantified, `PartialHomeomorph` is invoked with explicit `@`-syntax
   passing the topology instances.

4. **Euler form as a parameter** — Rather than constructing `chi(E,F) = sum_i (-1)^i dim Hom(E, F[i])`
   (which would require k-linear structure and dimension computation), the Euler form is
   taken as an abstract parameter `chi : K_0 C ->+ K_0 C ->+ Z`.

5. **`IsLimit`/`IsColimit` wrapped in `Nonempty`** — These are `Type`-valued in Mathlib,
   so `Nonempty` wrapping is needed to stay in `Prop`.

## Files Created

### File 1: `Mathlib/CategoryTheory/Triangulated/GrothendieckGroup.lean` (58 lines)

Defines the Grothendieck group `K_0 C` of a pretriangulated category.

**Definitions:**
- `K0Subgroup C` — the subgroup of `FreeAbelianGroup C` generated by:
  - `[X] - [Y]` for isomorphic objects `X ~ Y`
  - `[T.obj2] - [T.obj1] - [T.obj3]` for distinguished triangles `T`
- `K0 C` — the quotient `FreeAbelianGroup C / K0Subgroup C`
- `K0.instAddCommGroup` — the `AddCommGroup` instance
- `K0.of : C -> K0 C` — the class map

**Imports:** `Pretriangulated`, `FreeAbelianGroup`, `QuotientGroup.Defs`

### File 2: `Mathlib/CategoryTheory/Triangulated/Slicing.lean` (149 lines)

Defines slicings and supporting notions.

**Definitions:**
- `IsStrictMono` / `IsStrictEpi` — strict monomorphisms (kernels) and strict epimorphisms (cokernels)
- `QuasiAbelian` — class for categories where pullbacks of strict epis are strict epis, etc.
- `HNFiltration P E` — Harder-Narasimhan filtration data: a chain of distinguished triangles
  with semistable factors of strictly decreasing phases
- `Slicing C` — a slicing: phase function `P : R -> C -> Prop` with shift, Hom-vanishing,
  and HN existence axioms
- `Slicing.intervalProp` — the interval subcategory predicate `P((a,b))`
- `Slicing.IsLocallyFinite` — existence of `eta > 0` such that interval subcategories satisfy
  descending and ascending chain conditions for strict subobjects

**Imports:** `Pretriangulated`, `Kernels`, `Pullback.HasPullback`, `Data.Real.Basic`

### File 3: `Mathlib/CategoryTheory/Triangulated/StabilityCondition.lean` (133 lines)

Defines stability conditions and states the main theorems.

**Definitions:**
- `StabilityCondition C` — bundles:
  - `slicing : Slicing C`
  - `Z : K0 C ->+ C` (central charge)
  - `compat` — Z maps semistables to rays at the right phase angle
  - `locallyFinite` — the slicing is locally finite
- `bridgelandTheorem_1_2 : Prop` — Theorem 1.2
- `eulerFormRad` — radical of a bilinear form on K_0 (defined as `chi.ker`)
- `NumericalK0` — `K0 C / eulerFormRad C chi`
- `NumericalStabilityCondition` — stability conditions factoring through numerical K_0
- `NumericallyFinite` — class asserting `AddGroup.FG (NumericalK0 C chi)`
- `bridgelandCorollary_1_3 : Prop` — Corollary 1.3

**Imports:** `GrothendieckGroup`, `Slicing`, `PartialHomeomorph`, `Complex.Circle`,
`Finiteness`, `QuotientGroup.Defs`

## Errors Encountered During Implementation

### Error 1: `distTriang` notation precedence
**Symptom:** `And C` type mismatch at line 41 of GrothendieckGroup.lean.
**Cause:** `distTriang C` has precedence 60, so `T in distTriang C /\ ...` parsed as
`T in distTriang (C /\ ...)`.
**Fix:** Added parentheses: `(T in distTriang C) /\ ...`

### Error 2: Missing import for `R`
**Symptom:** Unknown identifier `R` in Slicing.lean.
**Cause:** `Pretriangulated` does not transitively import `Data.Real.Basic`.
**Fix:** Added explicit `import Mathlib.Data.Real.Basic`.

### Error 3: `IsLimit` is `Type` not `Prop`
**Symptom:** Type mismatch in `IsStrictMono`/`IsStrictEpi` definitions.
**Cause:** `IsLimit (KernelFork.of_iota f w)` has type `Type`, not `Prop`.
**Fix:** Wrapped with `Nonempty`: `Nonempty (IsLimit (KernelFork.of_iota f w))`.

## Post-Mortem

### Issue 1: Redundant isomorphism relations in `K₀Subgroup`

`K₀Subgroup` includes generators `[X] - [Y]` for `X ≅ Y` alongside the distinguished
triangle relations. This is redundant: for any isomorphism `f : X ≅ Y`, there is a
distinguished triangle `X → Y → 0 → X⟦1⟧`, so the triangle relation
`[Y] - [X] - [0]` already forces `[Y] = [X]`.

### Issue 2: `IsStrictMono`/`IsStrictEpi` duplicate existing Mathlib API

These redefine `NormalMono` and `NormalEpi` from
`Mathlib.CategoryTheory.Limits.Shapes.NormalMono.Basic`. The names also clash with
`StrictMono` (strictly monotone functions). Should use the existing Mathlib classes.

### Issue 3: `HNFiltration` is not abstracted to the right level

`HNFiltration` mixes two concerns: the tower structure (chain of distinguished triangles
with compatible objects) and the phase/semistability data. The right approach is:

1. A general **Postnikov tower** — a chain of distinguished triangles where consecutive
   triangles glue, defined categorically as a functor from a diagram shape category
   (following Mathlib's categorical packaging ethos, not `Fin n`-indexed arrays with
   explicit isomorphisms).
2. Phase data layered on top — `HNFiltration` becomes a Postnikov tower equipped with
   phases on the factors satisfying strict decrease and semistability.

The Postnikov tower abstraction composes with t-structures, weight structures, HN
filtrations, spectral sequences, and any "filtered object" notion in triangulated
categories.

### Issue 4: ACC/DCC chain conditions reinvented ad-hoc

`IsLocallyFinite` manually encodes ascending/descending chain conditions on strict
subobjects. Mathlib already has `WellFoundedGT`/`WellFoundedLT`, the
`IsNoetherian`/`IsArtinian` machinery, and `CategoryTheory.Subobject` with its lattice
structure. The chain conditions should be expressed through that infrastructure.

### Issue 5: Theorem 1.2 statement is mathematically incorrect

The formalization states the central charge map is a local homeomorphism onto all of
`K₀ C →+ ℂ`. Bridgeland's actual Theorem 1.2 says there exists a **linear subspace**
`V ⊆ Hom(K₀(D), ℂ)` such that the projection `Z : Stab(D) → V` is a local
homeomorphism. The current statement is strictly stronger than (and different from) the
actual theorem. Corollary 1.3 has a similar error.

### Issue 6: Locally finite categories never defined

The blueprint (B0) specifies that D is k-linear and of finite type, meaning
`⊕_i Hom_D(E, F[i])` is finite-dimensional over k for all E, F. This is the
prerequisite for the Euler form. The implementation skipped this entirely — there
is no `FiniteType` or k-linearity condition anywhere in the code.

### Issue 7: Euler form never constructed

The blueprint (B1) defines `χ(E,F) = Σ_i (-1)^i dim_k Hom_D(E, F[i])` as a
concrete construction from the k-linear structure. The implementation instead takes
`χ` as an abstract parameter `χ : K₀ C →+ K₀ C →+ ℤ`, meaning the numerical
Grothendieck group and all downstream definitions are relative to an arbitrary
bilinear form rather than the actual Euler form. The connection to the category's
Hom spaces is completely lost.

### Issue 8: The error originated in the plan, not the implementation

The plan itself misread the theorem statement. The user provided a blueprint markdown
file at the start of the conversation, but it was lost during context compaction. The
plan was then written from the AI's own understanding of the paper rather than faithfully
following the user's blueprint. The implementation faithfully followed the incorrect plan.

### Root Cause Analysis

The fundamental failures were:

1. **Blueprint not persisted to disk.** The user provided a detailed markdown blueprint
   with a dependency graph, precise theorem statements, node-by-node expansions, and
   concrete Mathlib identifiers to reuse. This existed only as a conversation message.
   When context was compacted, the summary preserved the *plan's* (already incorrect)
   interpretation rather than the blueprint's actual content. The blueprint's precise
   statement of Theorem 1.2 (with V(Σ), connected components, componentwise local
   homeomorphism), its K₀ definition (triangle relations only), its Mathlib reuse
   suggestions (NormalMono/NormalEpi, t-structures, hearts, connected components,
   ChartedSpace), and its dependency structure were all lost. **The blueprint should have
   been written to a file immediately upon receipt.**

2. **Plan diverged from blueprint without flagging it.** The plan was generated in plan
   mode and silently deviated from the blueprint on multiple points:
   - Dropped V(Σ) from Theorem 1.2
   - Added redundant isomorphism relations to K₀
   - Skipped phase bounds φ± as first-class objects
   - Ignored the blueprint's Mathlib reuse suggestions (NormalMono/NormalEpi,
     t-structures, ChartedSpace/IsManifold)
   - Replaced the blueprint's constructed topology (A8–A10) with ∃-quantification
   These deviations were never checked against the original blueprint.

3. **Insufficient reuse of existing Mathlib API.** The implementation created ad-hoc
   versions of concepts (`NormalMono`/`NormalEpi`, chain conditions) that already exist
   in Mathlib, rather than searching for and building on them. The blueprint explicitly
   listed concrete Mathlib identifiers to reuse.

4. **Wrong level of abstraction.** `HNFiltration` was built as a `Fin n`-indexed data
   structure with explicit isomorphisms rather than factored into a reusable categorical
   abstraction (Postnikov towers as functors from diagram categories) with domain-specific
   data layered on top. This violates Mathlib's categorical packaging ethos.

5. **The 4-agent review missed the major issues.** The review agents approved the code
   on style, documentation, proof quality, and generality grounds, but failed to catch
   the incorrect theorem statement, the duplicated API, the redundant K₀ generators, and
   the poor abstraction level. The review focused on surface-level conventions rather
   than mathematical and architectural correctness.

## Post-Mortem Round 2

The revised implementation (5 files, ~550 lines) fixed the 8 issues from round 1 but
introduced or retained the following problems.

### Issue 9: `eulerFormDescends` is a `Prop` definition, not a proved theorem

`eulerFormDescends` (NumericalStability.lean:77–82) is defined as a bare `def : Prop`,
stating that the Euler form is additive on distinguished triangles. For a locally finite
k-linear category (`IsFiniteType`), this should be a **proved theorem**: the proof follows
from the long exact sequence on shifted Hom spaces (`Triangle.coyoneda_exact₂/₃`) and
rank-nullity (`Submodule.finrank_quotient_add_finrank`).

Without the proof, the Euler form cannot be lifted to `K₀ C` via `QuotientAddGroup.lift`,
so `χ : K₀ C →+ K₀ C →+ ℤ` remains an abstract parameter throughout all downstream
definitions (`NumericalK₀`, `NumericallyFinite`, `NumericalStabilityCondition`,
`bridgelandCorollary_1_3`). This severs the connection between the numerical K-theory
and the actual categorical structure.

### Issue 10: `PostnikovTower` is still poorly designed

The structure stores `chain : ComposableArrows C n`, `factor : Fin n → C`, and
`triangle : Fin n → Triangle C` as three separate data fields, then stitches them
together with `Nonempty`-wrapped isomorphisms (`triangle_obj₁`, `triangle_obj₂`,
`triangle_obj₃`). This is highly redundant — the chain objects, triangle vertices, and
factors should not be independent data that happen to be isomorphic.

**Recommendation:** Study Mathlib's `SpectralObject` structure and API for how to
properly package filtration data in a triangulated/homological setting. That pattern
avoids the redundancy by making the diagram structure primary and deriving the
relationships, rather than asserting them via `Nonempty` isomorphisms.

### Issue 11: Theorems 1.2 and 1.3 should use `IsLocalHomeomorphOn`

Both `bridgelandTheorem_1_2` (StabilityCondition.lean:124–133) and
`bridgelandCorollary_1_3` (NumericalStability.lean:134–142) manually ∃-quantify over
`PartialHomeomorph` with explicit `@PartialHomeomorph ... τ₁ τ₂` topology parameters.

Mathlib already has `IsLocalHomeomorphOn` and `IsLocalHomeomorph` in
`Mathlib.Topology.IsLocalHomeomorph`, which encapsulate exactly this pattern:
`∀ x ∈ s, ∃ e : PartialHomeomorph X Y, x ∈ e.source ∧ f = e`.

Bridgeland's theorem says the central charge map `Z : Stab(D) → Hom(K₀(D), ℂ)` is a
local homeomorphism. The statement should be `IsLocalHomeomorphOn Z s` (or
`IsLocalHomeomorph Z` restricted to connected components), not a raw existential over
`PartialHomeomorph` with hand-threaded topology arguments.
